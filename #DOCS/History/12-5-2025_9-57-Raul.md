1. Estructuras y manejo de categorías

El módulo category define toda la lógica relacionada con categorías de productos dentro de los restaurantes. Las estructuras principales incluyen:

Category: Representa la categoría de un producto. Contiene:

restaurant_id: Uuid — Identificador del restaurante al que pertenece.

id: Uuid — Identificador único de la categoría.

name: String — Nombre descriptivo de la categoría.

CreateCategoryRequest, UpdateCategoryRequest, DeleteCategoryRequest: Estructuras que encapsulan los datos enviados por el cliente al crear, actualizar o eliminar una categoría. Cada una contiene la información mínima necesaria para ejecutar la acción en la base de datos.

La función create_category es asincrónica y recibe como parámetros:

path: web::Path<PathParams>: Extrae el id del restaurante desde la URL.

pool: web::Data<PgPool>: Conexión al pool de PostgreSQL usando sqlx.

body: web::Json<CreateCategoryRequest>: Contiene los datos enviados por el cliente en formato JSON.

El flujo de create_category es el siguiente:

Se genera un category_id con Uuid::new_v4().

Se ejecuta un INSERT en la tabla restaurantes.category_product con los valores id, restaurant_id y name.

Se maneja cualquier error SQL, transformándolo en un InternalServerError.

Se devuelve un HttpResponse::Ok con un JSON que confirma la creación de la categoría y devuelve su category_id.

Adicionalmente, se contempla la expansión para rutas de actualización y eliminación, siguiendo una estructura RESTful. El enrutamiento de categorías se configura con category_routes, creando un web::scope que permite agrupar todas las rutas de categorías bajo /restcategory/{id}/category.

2. Gestión de restaurantes

El módulo restaurants gestiona toda la lógica de creación, actualización, obtención y eliminación de restaurantes. Las estructuras principales son:

Restaurant: Modelo que representa un restaurante. Contiene campos como:

Identificadores (id, owner_id), información de contacto (address, phone, cellphone, email), datos de disponibilidad (is_available, accepts_reservations), detalles de negocio (cuisine_type, price_range, rating, slug) y URLs de branding (logo_url, cover_url). Además, timestamps created_at y updated_at permiten el seguimiento de la creación y modificación de registros.

CreateRestaurantRequest y UpdateRestaurantRequest: Estructuras que encapsulan los datos enviados por el cliente para crear o actualizar restaurantes. UpdateRestaurantRequest usa Option<T> para permitir actualizaciones parciales sin sobrescribir campos no especificados.

RestaurantSetting, RestaurantHour, RestaurantSpecialClosure: Modelos secundarios que permiten manejar configuraciones avanzadas, horarios de apertura/cierre y cierres especiales, respectivamente. Cada uno incorpora Uuid como identificador y timestamps para control histórico, usando tipos de fecha y hora de chrono para precisión temporal.

Las funciones principales de este módulo son:

create_restaurant:

Valida la autenticación mediante user_id obtenido desde los extensions del HttpRequest.

Genera un restaurante_id único.

Inserta los datos en restaurantes.restaurants usando sqlx::query.

Devuelve un HttpResponse con la confirmación de creación y el ID generado.

get_my_restaurants:

Obtiene todos los restaurantes pertenecientes al user_id.

Ejecuta un SELECT ordenado por created_at DESC para mostrar primero los registros más recientes.

Devuelve un JSON con la lista de restaurantes.

get_restaurant:

Recupera un restaurante específico por id y valida la propiedad mediante owner_id.

Si no se encuentra, devuelve NotFound.

update_restaurant:

Permite actualizar datos específicos usando COALESCE, de modo que solo los campos provistos se modifiquen.

Incluye la actualización de la marca temporal updated_at con NOW().

delete_restaurant:

Elimina un restaurante específico validando la propiedad mediante owner_id.

Maneja errores SQL de manera segura y retorna un mensaje de confirmación.

El enrutamiento de restaurantes se define en restaurant_routes(), agrupando todas las operaciones CRUD bajo /restaurants, asegurando consistencia RESTful.

3. Gestión de usuarios y autenticación

El módulo users junto con auth se encarga de manejar usuarios, registro, login y autenticación basada en JWT y cookies.

Estructuras clave:

User:

Información básica (id, nombre, apellido, email), seguridad (password_hash) y estado (activo, suscripcion, tipo_suscripcion).

El campo rol: RolUsuario define el tipo de usuario (Empresa o Usuario).

RegisterUser y LoginUser:

Modelos para encapsular la información requerida al registrar o autenticar usuarios.

RolUsuario:

Enumeración para tipar los roles de usuarios de manera estricta.

Flujo de servicios de usuario:

register_user_service:

Hash de la contraseña usando bcrypt.

Creación del usuario en la tabla auth.users.

Generación de JWT para autenticación y refresh token.

Creación de cookies de acceso y refresh que se retornan al cliente.

Devuelve un AuthResponse con cookies y JSON del usuario.

login_user_service:

Busca al usuario por email.

Verifica si el usuario está activo.

Valida la contraseña contra el hash almacenado.

Genera JWT y refresh token, almacenando este último en la base de datos.

Devuelve AuthResponse.

get_user_profile_service:

Recupera información del usuario desde la base de datos usando user_id.

Maneja errores de manera detallada.

El enrutamiento de usuarios se realiza mediante user_routes, agrupando todas las rutas relacionadas con autenticación bajo /user, incluyendo register, login, refresh y logout.

4. Integración y arquitectura general

El main del proyecto implementa un servidor Actix Web configurado con las siguientes características:

CORS:

Configurado para permitir solicitudes desde el frontend (http://192.168.100.17:5173).

Soporta métodos GET, POST, PUT, DELETE y headers como CONTENT_TYPE, AUTHORIZATION, ACCEPT.

Permite credenciales para soportar cookies de autenticación.

Scopes de rutas:

/auth → Rutas públicas para registro y login.

/api → Rutas protegidas mediante AuthMiddleware, incluyendo:

/profile → Información del usuario autenticado.

/suscripcion → Creación de suscripciones.

Rutas CRUD para restaurantes y categorías.

Middleware:

AuthMiddleware intercepta solicitudes para validar JWT y asegurar que solo usuarios autenticados puedan acceder a rutas protegidas.

Pool de base de datos:

Conexión asincrónica a PostgreSQL mediante sqlx.

Pool compartido entre los distintos módulos mediante web::Data.

Logger:

Se inicializa con env_logger para capturar logs con niveles configurables desde .env.

Documentación futura:

Hay referencias a Swagger (utoipa_swagger_ui) para generar documentación de API de manera automática, aunque está comentada.

5. Patrones y buenas prácticas

El código refleja varias buenas prácticas de desarrollo en Rust:

Tipado fuerte y seguridad de memoria:

Uso de Uuid para identificadores universales.

Option<T> para campos que pueden ser nulos.

serde para serialización/deserialización segura entre Rust y JSON.

Separación de responsabilidades:

Cada módulo (users, restaurants, category, auth) maneja un dominio específico.

Funciones de repositorio (repositories_users) separadas de handlers, siguiendo principios de Clean Architecture.

Manejo de errores robusto:

Captura de errores SQL y de validación de autenticación.

Uso de map_err para convertir errores internos en respuestas HTTP adecuadas.

Asincronía:

Todas las operaciones de base de datos y HTTP son async, aprovechando la eficiencia de Actix Web para manejar múltiples conexiones simultáneamente.

Escalabilidad y mantenibilidad:

Modularización clara.

Uso de scopes (web::scope) para agrupar rutas.

Funciones reutilizables para servicios de usuario y gestión de tokens.

Seguridad:

Hash de contraseñas con bcrypt.

Refresh tokens almacenados en la base de datos.

Cookies con tokens JWT para acceso autenticado.

6. Resumen conceptual de flujo completo

Registro/Login de usuario:

Cliente envía datos → Servidor valida y crea hash → Guarda usuario → Genera JWT y refresh token → Retorna cookies y datos.

Gestión de restaurantes:

Usuario autenticado realiza CRUD sobre restaurantes.

Validaciones de propiedad mediante owner_id.

Actualizaciones parciales con COALESCE.

Gestión de categorías:

CRUD sobre categorías de productos vinculadas a un restaurante.

Cada categoría tiene un UUID único.

Manejo de errores SQL y respuestas JSON.

Middleware y seguridad:

Rutas públicas (registro, login) vs. rutas protegidas (/api).

Autenticación JWT en cada petición protegida.

CORS configurado para permitir frontend específico.

Base de datos y modelos:

PostgreSQL gestionado mediante sqlx.

Tablas para restaurants, category_product, users, refresh_tokens, restaurant_settings, restaurant_hours, restaurant_special_closures.

Tipos de datos complejos (NaiveDateTime, BigDecimal, serde_json::Value) para cubrir todos los casos de negocio.

En conclusión, este proyecto constituye un backend completo y profesional, preparado para manejar usuarios, autenticación segura, restaurantes y categorías de productos, con un enfoque RESTful, asincrónico y modular. La integración de Rust, Actix Web, PostgreSQL y JWT permite una aplicación escalable, segura y eficiente, lista para ser conectada con un frontend moderno y extendida con nuevas funcionalidades como productos, pedidos, suscripciones o reportes avanzados.
